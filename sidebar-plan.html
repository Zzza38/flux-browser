Flux Browser · implementation plan

Websites belong
in the sidebar.

Build an Opera-style web-app rail directly into Chromium, but let users pin any normal website. Panels share the active profile, shrink the page, sync across devices, and unload cleanly after three idle minutes.

Architecture

Separate feature, native Chromium pieces

Flux integrates with BrowserView but owns its rail, state, and web contents. Reuse side-panel patterns without coupling arbitrary websites to Reading List and extension panels.

FluxSidebarCoordinator

Window-scoped visibility, active sites, split layout, timers, and commands.

→
FluxSidebarView

52px rail, resizable host, toolbar, split container, and accessibility.

→
FluxSiteContents

Profile-backed WebContents, navigation, permissions, audio, discard, and reload.

Boundary: reuse concepts and helpers from chrome/browser/ui/views/side_panel/, but keep Flux in a separate coordinator so existing Chrome side panels do not inherit web-app behavior.

Roadmap

Six phases, each ending in proof

A successful compile is not a feature. Each phase ends with browser-visible behavior or a test demonstrating the actual contract.

Phase 00Foundation

Baseline and feature boundary

Prove the fork builds and launches, then establish a disabled-by-default feature flag and isolated component boundary.

Build

  • Generate a clean desktop build directory.
  • Build and launch the current fork once.
  • Record upstream revision and GN args.

Scaffold

  • Add kFluxSidebar.
  • Create model, coordinator, and Views targets.
  • Keep it off until the shell is usable.

Exit gate

  • Stock browser launches.
  • Flag appears in chrome://flags.
  • Toggling it causes no UI regression.
Likely touchpointschrome/common/chrome_features.*chrome/browser/about_flags.ccchrome/browser/ui/browser_window/internal/browser_window_features.cc
Phase 01Native shell

Rail, panel host, and resizing

Add the left rail to the desktop frame. Opening a site consumes layout width so the webpage visibly shrinks.

Rail

  • 52px native Views rail inside BrowserView.
  • Top actions, pinned sites, bottom utilities.
  • Same icon opens and closes its panel.

Geometry

  • Start at 25% of browser content width.
  • Clamp only to 10% minimum and remaining page width.
  • Persist width and support drag resize.

Exit gate

  • Rail survives tabs and navigation.
  • Panel shrinks, never covers, the page.
  • Narrow-window behavior passes.
Reuse and extendchrome/browser/ui/views/frame/browser_view.*chrome/browser/ui/views/side_panel/side_panel.*chrome/browser/ui/views/side_panel/side_panel_resize_area.*
Phase 02Arbitrary websites

Pin, manage, and sync normal URLs

Turn the shell into a user-owned website list with durable ordering and no service-specific code.

Site model

  • ID, title, last URL, favicon, order, muted state.
  • Accept HTTP(S); reject privileged schemes.
  • Add, edit, remove, and drag to reorder.

Profile data

  • Store pins in syncable profile preferences.
  • Use the active Profile storage partition.
  • Use standard OffTheRecord behavior in Incognito.

Exit gate

  • Added URLs open and sign in normally.
  • Restart preserves list and order.
  • A synced profile receives the pins.
Likely touchpointscomponents/prefs/components/sync_preferences/components/favicon/chrome/browser/profiles/profile.*
Phase 03Web contents

Real pages and the three-minute lifecycle

Host sites as proper WebContents, not iframes. Keep inactive sites instant for three minutes, then reclaim their renderer.

Navigation

  • Links, redirects, auth popups, downloads, permissions.
  • Reload, back, forward, mute, open in tab.
  • Keep browser security indicators truthful.

Lifecycle

  • Active → Warm → Discarded.
  • Restart a three-minute timer on deactivation.
  • Retain last committed URL, then destroy contents.

Exit gate

  • Renderer exists at 2:59 and is gone after 3:00.
  • Reopening reloads the last URL.
  • Shared-profile cookies remain available.
Core APIscontent/public/browser/web_contents.hcontent/public/browser/web_contents_observer.hui/views/controls/webview/webview.h
Phase 04Multitasking

Two-site split and Opera-style controls

Allow exactly two sidebar sites at once without turning the browser into a tiling-window-manager thesis project.

Split host

  • Side-by-side by default.
  • Toggle top/bottom without reloading.
  • Independent focus, navigation, audio, and resize state.

Interaction polish

  • Three-dot setup and removable starter pins.
  • Notification badges and mute indicators.
  • Keyboard order, tooltips, and shortcuts.

Exit gate

  • Both sites work simultaneously.
  • Layout switching preserves both renderers.
  • Keyboard and screen-reader navigation pass.
Phase 05Release gate

Cross-platform hardening

Ship only after this behaves like a browser surface rather than a particularly ambitious demo.

Automated coverage

  • Model, preference, and lifecycle unit tests.
  • Coordinator browser and Views interaction tests.
  • Split, sync, and Incognito coverage.

Manual matrix

  • Windows, macOS, and Linux builds.
  • OAuth, passkeys, downloads, media, notifications.
  • Narrow windows, scaling, multi-monitor, RTL.

Exit gate

  • No existing Chrome side-panel regressions.
  • Clean restart and profile migration.
  • No Opera assets or proprietary code.

Scope control

What v1 is, and what it is not

Required for v1

  • Native rail and shrinking panel
  • Arbitrary normal websites
  • Shared cookies and normal Incognito
  • Three-minute renderer cleanup
  • Two-site split
  • Cross-platform desktop support

Explicitly deferred

  • Restoring scroll, forms, or media position
  • A separate sidebar cookie jar
  • More than two visible sites
  • Mobile Chromium support
  • Opera artwork or proprietary code
  • Service-specific integrations
